llm-d
=====

`llm-d <https://llm-d.ai>`__ is a Kubernetes-native orchestration layer that runs on top
of `vLLM <https://docs.vllm.ai>`__ to deliver production-scale LLM inference. It adds
intelligent prefix-cache-aware routing, prefill/decode (PD) disaggregation, and
workload-aware autoscaling through a standard Helm-based deployment workflow.

.. note::

   llm-d requires the QAIC vLLM image as its model server — vLLM runs inside every
   prefill and decode pod. See :doc:`/Getting-Started/Model-Serving/vLLM-Serving/index`
   for available image tags and vLLM-specific configuration.

Qualcomm Cloud AI 100 support is available through QAIC patch files shipped with the SDK.
These patches extend the upstream llm-d and llm-d-modelservice Helm charts with QAIC
accelerator configuration, custom proxy containers, and KV-handoff integration.

Architecture
------------

Prefill-Decode (PD) disaggregation separates the two phases of LLM token generation onto
dedicated pods:

- **Prefill pods** — process the input prompt (compute-intensive, short-lived per request).
- **Decode pods** — generate output tokens iteratively (memory-bandwidth-intensive, long-lived per request).

Separating these phases eliminates prefill interference with decode latency, enabling lower
inter-token latency (ITL) and higher throughput for long-context workloads.

E-PD (Encode-Prefill-Decode for VLMs)
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

The encode model runs inside the prefill pod. A custom proxy sidecar in the decode pod
routes encode requests to the prefill service (port 9900) and decode requests to the
vLLM decode backend (port 9800). The GAIE InferencePool targets decode pods only.

.. code-block:: text

                        Client
                           |
                           v
              +------------------------+
              |   Inference Gateway    |
              |   (Istio)  :80         |
              +----------+-------------+
                         |
                         v
              +------------------------+
              |   GAIE EPP             |
              |   InferencePool        |
              |   (decode pods only)   |
              +----------+-------------+
                         |
                         v
              +------------------------------+
              |   Decode Pod                 |
              |  +------------------------+  |
              |  |  Custom Proxy  :8000   |  |
              |  +----+----------+--------+  |
              |       |          |           |
              | encode|    decode|           |
              | reqs  |    reqs  |           |
              +-------+----------+-----------+
                      |          |
                      v          v
            +-----------+    +-----------+
            | Prefill/  |    |  vLLM     |
            | Encode Pod|    |  Decode   |
            | :9900     |    |  :9800    |
            | (encode   |    |  (token   |
            |  model)   |    |   gen)    |

Autoscaling Architecture
~~~~~~~~~~~~~~~~~~~~~~~~

The Workload Variant Autoscaler (WVA) scales prefill and decode independently using
KV cache utilization and request queue depth — not CPU or GPU — as the saturation signal.

.. image:: wva_architecture.png
   :alt: WVA architecture — two independent controllers emitting wva_desired_replicas consumed by separate HPAs
   :align: center
   :width: 650

Each reconciliation cycle (~60 s), WVA:

1. Collects peak KV cache usage and queue depth from Prometheus for all pods of the model
   (using ``max_over_time[1m]`` for safety).
2. Identifies non-saturated replicas: those where ``kv_cache < threshold`` **and**
   ``queue < threshold``.
3. Calculates average spare capacity across non-saturated replicas.
4. Triggers **scale-up** if average spare KV cache ``< kvSpareTrigger`` **or** average
   spare queue ``< queueSpareTrigger``.
5. Simulates **scale-down** safety: redistributes total load across ``N-1`` replicas; only
   scales down if the result still has sufficient headroom.
6. Emits ``wva_desired_replicas`` to Prometheus; HPA reads this and scales the Deployment.

Cascade scaling protection: WVA skips variants with pending (not-yet-ready) pods during
scale-up selection, preventing over-provisioning during the model-loading window.

Helm Releases
~~~~~~~~~~~~~

Every deployment uses three coordinated Helm releases:

.. list-table::
   :header-rows: 1
   :widths: 20 25 55

   * - Release
     - Chart
     - Purpose
   * - ``ms-pd-qaic``
     - llm-d-modelservice
     - Deploys prefill + decode pods, routing sidecar, kv-handoff-server
   * - ``gaie-pd-qaic``
     - inferencepool (GAIE)
     - Deploys the EPP router and InferencePool targeting decode pods
   * - ``infra-pd-qaic``
     - llm-d-infra
     - Deploys the Istio Inference Gateway

Setup Steps
-----------

.. list-table::
   :header-rows: 0
   :widths: 15 85

   * - **Step 0**
     - Kubernetes cluster (v1.33.0+) with the QAIC device plugin running.
       See :doc:`../index` for device plugin setup instructions.
   * - **Step 1**
     - :doc:`qaic-integration` — clone and patch the llm-d repos, install Istio,
       generate the model service configuration.
   * - **Step 2**
     - :doc:`disaggregation` — deploy PD or E-PD disaggregated serving.
   * - **Step 3**
     - :doc:`autoscaling` — deploy the Workload Variant Autoscaler (WVA).
